## 1. 目标与使用者价值

将现有截图 MCP 扩展为稳定、可复用的屏幕视觉输入服务，让支持图像的 AI 客户端能够选择截图目标、直接获取图片、识别文字，并引用此前的截图继续分析。

主要使用场景：

- “查看副屏的错误并分析原因”：查询显示器 → 指定显示器截图 → 客户端模型分析。
- “提取当前窗口的文字”：截图 → OCR → 返回文字和位置。
- “继续分析刚才那张图”：通过截图 ID 读取同一份结果，避免重新截图后内容变化。

MCP 负责捕获、传输和 OCR；错误分析、表格理解与 CSV 生成由客户端模型完成，不能将这些描述为截图服务自身保证的能力。

## 2. 当前实现与问题

基于当前仓库静态检查：

| 位置 | 现状 | 改造理由 |
| --- | --- | --- |
| `src-tauri/src/mcp/mod.rs` | 只有 `take_screenshot`，接收 `mode` / `monitor_index`，返回换行分隔的文件路径 | 客户端必须另外读取文件才能看图，缺少结构化元数据 |
| `src-tauri/src/mcp/mod.rs` | 文件名使用秒级时间戳 | 同一秒内多个请求可能覆盖文件 |
| `src-tauri/src/mcp/mod.rs` | 捕获在阻塞任务内，PNG 编码及写盘在异步处理函数中 | 编码和磁盘操作可能占用异步执行线程 |
| `src-tauri/src/mcp/capture.rs` | 指定显示器截图先捕获全部显示器再取一张 | 增加延迟、内存和无关屏幕捕获 |
| `src-tauri/src/main.rs` | stdio 使用全局单实例锁 | 不同客户端同时启动独立 stdio 服务时，后启动者退出 |
| `src-tauri/src/main.rs` | HTTP 默认端口 3000，启动前先探测再绑定 | 端口探测存在竞态，应直接绑定并处理错误 |
| 三份 README | 展示端口 8787，工具签名写为 `target, path` | 与实际参数不一致；端口示例需要明确是显式配置值 |
| HTTP 启动入口 | 绑定回环地址，使用 rmcp 默认配置；应用层未显式配置认证与 Origin 策略 | 需核实依赖层已有保护，并补齐应用层策略和测试 |
| 截图存储 | 固定保存到用户目录下 `.clover-viewer/tmp`，无自动清理 | 长期使用积累文件，缺少明确的保留周期 |

实施前重新检查依赖版本、工作区变更和实际客户端行为；以上是静态发现，不是已完成的运行时验证。

## 3. 范围和设计原则

- 保留 stdio 与 Streamable HTTP，以及已有 `take_screenshot` 名称和旧参数语义。
- 先保证旧调用稳定，再增加图片返回、资源读取和 OCR。
- 保留独立无窗口运行方式；共享核心服务不依赖 Tauri 窗口或前端初始化。
- 首轮 HTTP 仅支持本机访问，不增加局域网服务、远程部署或通用桌面操作。
- 滚动截图、鼠标键盘控制、持续监控与 GUI 管理页面作为后续独立需求。

## 4. 分阶段修改

### 阶段一：基础正确性与兼容修复

工作项：

1. 统一三份 README 的真实参数、默认端口和调用示例；默认端口保留 3000，8787 作为显式指定示例。
2. 文件名引入跨进程唯一 ID，并使用排他创建避免覆盖；失败时清理本次产生的残缺文件。
3. 显示器截图改为先枚举、选择目标，再捕获目标；定义索引规则，避免因过滤条目造成静默错位。
4. 将编码与写盘移入阻塞任务。
5. 在内部使用类型化模式和统一参数校验，保留“不传 mode 但传 monitor_index”的兼容行为。
6. 区分参数错误、工具执行失败和协议内部错误；提供稳定业务错误码与可理解说明。
7. HTTP 直接绑定端口，明确报告占用错误；非法端口参数不能静默退回默认值。
8. stdio 按客户端进程隔离，移除全局互斥限制；先保证跨进程文件唯一性。核实日志始终不污染协议 stdout。

验收：旧参数调用继续成功；同秒并发不覆盖；指定屏幕不捕获其他屏幕；两个 stdio 客户端可同时工作；无效参数返回明确错误。

### 阶段二：服务层与截图存储

建议结构（实际命名可随现有模块调整）：

```text
src-tauri/src/
  capture_service/      # 目标枚举、捕获、坐标和图像元数据
  artifact_store/       # 截图 ID、存取、配额、过期清理
  mcp/
    mod.rs             # 协议组装
    tools.rs           # 输入校验和结果转换
    transport.rs       # stdio / HTTP 生命周期
    config.rs          # 服务配置
```

工作项：

1. 将捕获与存储从 MCP 协议处理中分离；评估现有 GUI 截图和 OCR 的可复用部分，避免将前端状态引入服务层。
2. 为截图分配不透明 `capture_id`，记录时间、目标、坐标、原始尺寸、返回尺寸、格式和文件大小。
3. 支持过期时间与磁盘配额；仅清理存储组件自己登记的文件，不遍历删除旧目录中的任意文件。
4. 默认保留周期建议 24 小时、容量上限建议 512 MiB，均可配置；实施时根据实际图片体积验证默认值。
5. 明确重启后的 ID 策略：保存必要索引并恢复未过期截图；缺失文件或过期 ID 返回明确错误。
6. 处理写入、读取、删除、过期清理的竞争；多个独立 stdio 进程使用隔离的存储命名空间，避免互相清理。

验收：MCP 无需了解文件命名细节；截图 ID 可重复读取同一图像；重启恢复、配额、过期与读取竞争行为有测试；GUI 原有流程正常。

### 阶段三：直接返回图像与目标发现

工具设计：

| 工具 | 作用 | 主要输入 |
| --- | --- | --- |
| `list_monitors` | 查询显示器与坐标信息 | 无 |
| `take_screenshot` | 截图并选择交付形式 | 旧参数，以及 `monitor_id`、`region`、`delivery`、`max_width` |
| `get_screenshot` | 获取已生成截图 | `capture_id`、`delivery`、`max_width` |
| `delete_screenshot` | 显式删除本服务的截图 | `capture_id` |

工作项：

1. 增加 `delivery: path | image | both`。省略该参数时默认返回 `image`，使视觉客户端无需依赖服务端本地路径；`path` 作为显式兼容选项保留。
2. 增加符合输出 schema 的结构化元数据。图片交付不包含可能在客户端不可访问的服务端路径；仅 `both` 包含该路径，`path` 继续保留路径文本兼容表示。
3. 图片使用 MCP `ImageContent` 返回；设置最大宽度、总像素和编码字节上限，多屏结果按请求总量限制，避免一次返回过多图片。
4. 返回原始尺寸、实际返回尺寸和缩放比例，方便客户端把图像坐标映射回屏幕。
5. `list_monitors` 返回 ID、当前索引、名称、位置、尺寸、主屏标志；缩放信息仅在可靠获取时返回。
6. 核实底层显示器 ID 的稳定性，不承诺硬件变更或重启后不变；失效 ID 明确报错，不静默切换目标。
7. `region` 采用虚拟桌面物理像素坐标，支持负坐标；首轮限定区域完整位于单个显示器内，越界或跨屏明确报错。
8. 明确参数冲突规则：ID 与索引不可同时指定；模式与目标不匹配时拒绝调用。

验收：支持图像的客户端无需读取本地文件即可看图；旧路径调用不变；混合 DPI、负坐标、热插拔、缩放及体积限制行为清晰。默认截图目标仍是活动窗口。

### 阶段四：OCR 集成

工作项：

1. 新增 `ocr_screenshot(capture_id, language?)`，复用现有 Windows OCR 能力，对存储的原图识别。
2. 返回完整文本、行文本和可用的位置数据；明确坐标基于原始截图。
3. 明确语言不可用、截图过期、无文字和识别失败的返回行为；无文字作为正常空结果。
4. 对 OCR 的尺寸限制、预处理缩放和坐标还原进行适配。
5. 首轮仅接收本服务的截图 ID，不开放任意文件路径读取。

验收：实际可用语言下的中英日样本可识别；坐标与原图对齐；无文字与失败可区分；无需启动 GUI。

### 阶段五：本地 HTTP 安全与运行管理

工作项：

1. 检查 rmcp 实际版本的传输保护，显式配置并测试 Origin 校验，拒绝不可信网页来源；兼容不发送 Origin 的本地原生客户端。
2. HTTP 使用本地随机 Bearer Token，支持受限权限的 token 文件；日志与响应不得泄漏凭据。此方式面向本地接入，不宣称实现完整 OAuth 授权发现。
3. 保持回环地址绑定；首轮不提供任意 `--bind`，避免不完整的远程访问支持。
4. 增加 `--data-dir`、`--token-file` 和保留策略配置，统一配置优先级与帮助信息；stdio 不引入 HTTP 认证流程。
5. 增加请求并发限制、有限排队、超时、响应体积限制和正常关闭处理。
6. 明确阻塞捕获不能因外层超时自动停止；资源占用上限须覆盖仍在执行的后台工作，避免超时后持续堆积。
7. 日志包含请求 ID、耗时、目标类型和错误码，默认不记录图像、OCR 正文或窗口标题。
8. 文档提供带认证的 HTTP 接入示例；认证启用属于 HTTP 接入方式变化，需要迁移说明。

验收：未授权请求失败；可信客户端能完成握手与截图；不可信 Origin 被拒绝；高并发与超时不导致无界任务堆积；日志不污染 stdio 协议。

## 5. 验证与交付

- 单元测试：参数组合、坐标换算、ID 生命周期、并发存储、配额与错误映射。
- 协议集成测试：两种传输的初始化、工具列表、调用、图片结果、失败和断开；旧参数兼容单独覆盖。
- 使用可注入的捕获实现测试无显示器、捕获失败及并发，避免自动化测试依赖真实桌面状态。
- Windows 实机验证：多屏、混合 DPI、负坐标、无活动窗口、显示器变更及 OCR。
- 使用至少一个支持图片内容的 MCP 客户端验证完整链路；记录客户端与协议版本及不支持的能力。
- 对比单屏/多屏截图的耗时、内存和输出大小，确认目标屏幕捕获优化有效。
- 每阶段独立交付代码、相应测试和中英日文档更新，便于审查与回退。

建议首个交付批次覆盖阶段一至三，提供稳定截图、显示器发现和直接看图；第二批加入 OCR。HTTP 安全应在新版 HTTP 功能发布前完成，即使其工作与前面阶段并行开展。
