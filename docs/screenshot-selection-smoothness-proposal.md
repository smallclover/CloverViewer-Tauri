# 截图选区拖动流畅度优化提案

日期：2026-10-08  
状态：底图/选区分层与独立放大镜已实施，功能和绘制次数检查通过；真实 WebView2 的帧率与观感验收待完成。记录见 [优化验证](screenshot-selection-smoothness-validation.md)。

## 1. 问题与目标

用户反馈：按住鼠标拖动框选，选区不断变大、变小时，跟随过程不够丝滑，感觉刷新帧数不足。位置能够正确跟随，没有观察到选框跳到错误坐标。

建议将普通截图的静态底图、选区遮罩与边框、标注、放大镜分开更新。选区变化不再触发整张虚拟桌面画布的清空和底图重绘，让拖动时的工作主要由小范围绘制和简单的显示几何更新组成。

本轮目标：

- 改善普通截图中按住鼠标创建选区的连续感，包括跨屏和反向拖动。
- 保留当前截图清晰度、尺寸标注、放大镜取色与导出结果。
- 以帧耗时和实际桌面体验验收；记录不同屏幕配置下的结果。
- 沿用截图就绪前的窗口尺寸校验，保持双屏画面和坐标正确。

已确定选区的移动、窗口自动框选和标注交互需要回归验证。滚动截图保留现有渲染路径，验证切换时的透明捕获区域；本提案不扩展其拼接算法，也不新增设置项。

## 2. 当前路径与性能嫌疑

相关代码：

| 模块 | 当前职责与观察 |
| --- | --- |
| `src/screenshot/editor-input.ts` | 更新拖动起点、当前位置和交互状态，请求刷新。原生窗口探测只在未拖动的悬停阶段执行。 |
| `src/image-editor/frame-update.ts` | 已使用 `requestAnimationFrame` 合并刷新请求，每帧消费最新状态。 |
| `src/screenshot.ts` | 根据临时拖动状态计算预览矩形，调度画布渲染与浮层。 |
| `src/screenshot/editor-renderer.ts` | 选区坐标进入帧比较；坐标改变时使用整个画布作为重绘区域。放大镜存在时也走整幅重绘。 |
| `src/screenshot/magnifier.ts` | 每次绘制采样 15×15 像素并读取颜色，再以 225 个色块绘制放大区域。 |
| `src/screenshot/editor-ui-controller.ts` | 已缓存布局状态；首次框选期间持久选区仍为空，工具栏通常不会逐帧重新定位。 |

原始多屏画面已经缓存，但显示画布仍反复执行：清空整幅画布、复制原图、叠加压暗遮罩、在选区内恢复原图，再画边框和放大镜。双 1080p 横向排列的画布为 3840×1080，约 415 万像素；双 4K 横向排列约为 1659 万像素。

因此首要嫌疑是每帧处理的面积和绘制工作量。放大镜采样读取还可能造成同步等待，需通过跟踪验证。事件合帧、底图缓存、根坐标缓存和窗口探测节流已有实现，应在这些基础上优化。

此前新增的 `viewport-ready.ts` 只在截图加载和显示前工作，不进入鼠标拖动的刷新路径。多屏尺寸校验与拖动流畅度分别验收。

## 3. 建议方案

### 3.1 静态底图与选区显示分层

普通截图显示由以下层组成，数据仍使用原图物理坐标：

| 层 | 内容 | 更新条件 |
| --- | --- | --- |
| 静态底图 | 本次捕获的完整桌面，包含多屏之间的空白区域 | 新截图、源数据或显示布局改变 |
| 标注层 | 已提交标注与当前标注预览 | 标注变化，继续复用现有局部更新与缓存 |
| 选区层 | 四块压暗遮罩、绿色边框、手柄与尺寸标签 | 选区、悬停窗口或显示布局改变 |
| 放大镜层 | 小尺寸放大镜与颜色、坐标提示 | 采样位置、提示状态或显示布局改变 |
| 操作浮层 | 工具栏、帮助、文本输入和弹出面板 | 原有交互与必要的布局变化 |

优先采用四块绝对定位遮罩和独立的选框元素。每帧集中写入显示几何，避免在写入之后立即读取布局；评估用 `transform` 更新遮罩和位置。尺寸标签仅在取整后的宽高改变时更新。

初始悬停继续显示窗口绿框；用户开始框选后才显示选区外遮罩，保留当前行为。初次框选结束后再显示操作工具栏。

静态底图每次捕获只合成一次，优先复用现有源画布。进入纯框选路径后，不因选区或放大镜变化对整幅底图调用 `clearRect`、`drawImage`，也不逐帧生成 PNG 或 data URL。标注画布作为透明层使用，保留输入命中平面，避免分层后鼠标事件落不到原控制器。

DOM 分层是否减少浏览器绘制和合成成本必须实测；不对全部元素强制开启独立合成层，也不预设 `clip-path` 一定能免费更新。如果分层后合成仍是瓶颈，再比较局部更新方案。

### 3.2 放大镜独立更新

将放大镜从整幅编辑画布移到一个固定屏幕尺寸的小画布，位置更新与采样绘制分离。保留当前开关、配色、取色快捷键、边缘避让及跨屏行为。

建议实施顺序：

1. 迁移到独立小画布，使放大镜移动不再要求整幅画布重绘。
2. 将 15×15 采样通过关闭图像平滑后放大绘制，替代 225 次逐色块填充；中心像素边框和文字单独绘制。用像素校验确认显示与取色一致。
3. 缓存采样的整数坐标和当前截图编号。同一像素位置只更新显示位置；颜色复制反馈单独失效，不必重新采样。
4. 记录采样耗时。仅在存在明显读回开销时比较小采样画布的 `willReadFrequently` 或直接读取 RGBA 的方案。后者需要评估额外保留原始像素数组的内存成本。

选框与放大镜位置继续跟随显示帧。首轮保留原有放大镜能力；降低采样频率只作为测量后可比较的方案。

### 3.3 拖动状态与收尾

- 继续每帧只消费最新的框选位置，不增加会堆积的鼠标事件队列。
- 对笔画与马赛克保留有效路径点，不能将选区的“只保留最新位置”策略直接用于笔画采样。
- 框选释放时以鼠标抬起事件的坐标计算最终矩形，并同步提交最终显示状态。当前框选分支主要使用最后一次移动的位置，实施时补齐这一边界。
- 取消、关闭、重新框选和新截图到来时，撤销待处理刷新并清理各显示层，避免残影和旧会话重新出现。
- 拖动期间复用布局和坐标映射；窗口或倍率变化使缓存失效。统一从现有物理坐标转换到 CSS 坐标，不在新模块中引入第二套换算。
- 窗口悬停探测保持现有节流；创建选区期间继续禁止探测。

### 3.4 与导出、滚动截图的衔接

原始像素、标注及导出维持独立的数据路径。保存、复制、OCR 和分享继续从原始屏幕画面及标注合成，选框、遮罩、放大镜和操作浮层均不进入输出。

进入滚动截图时，必须在捕获开始前隐藏普通截图的静态底图、选区层与放大镜层，保留现有选区透明挖空逻辑。仅清空标注画布不足以让新增的底图层透明，必须明确管理整个显示模式的显隐。

负坐标副屏、上下错位的多屏、混合 DPI、用户界面倍率与不同刷新率显示器均列入验证。跨屏覆盖窗口实际采用的刷新节奏以运行时测量为准。

## 4. 模块边界与实施顺序

建议增加 `src/screenshot/selection-overlay.ts` 管理遮罩、边框和标签，增加 `src/screenshot/magnifier-overlay.ts` 管理放大镜小画布及显隐。静态底图显示可使用独立模块或明确的渲染器接口，按实际实现选择。

`screenshot.ts` 保持组合职责，`editor-input.ts` 保持交互状态职责。源画面合成继续复用 `screen-compositor.ts`，标注继续复用现有标注层。首轮预计不需要新增 Tauri 命令、配置字段或用户可见文案；若实施时确实需要，则遵守 `src/api.ts` 契约优先和三语同步规则。新增业务模块默认不超过 500 有效代码行。

| 阶段 | 工作 | 阶段产物与判定 |
| --- | --- | --- |
| A：建立基线 | 测量普通框选；比较放大镜开启/关闭及单屏/双屏 | 保存环境、帧间隔、JS 耗时和浏览器跟踪，确认主要耗时位置 |
| B：底图与选区分层 | 实现静态显示、选区层、最终坐标收尾及模式清理 | 纯框选过程中没有整幅底图重绘；尺寸、跨屏和释放坐标正确 |
| C：放大镜分层 | 独立小画布、减少绘制调用、采样缓存 | 取色和视觉一致，移动不触发整幅绘制；帧耗时进一步对比 |
| D：回归与验收 | 跑真实 WebView2 性能测试及坐标、导出、滚动截图回归 | 输出优化前后对照；根据结果决定是否需要额外优化 |

每阶段记录实际收益。先完成 B、C，再根据测量判断是否需要后台线程、OffscreenCanvas、WebGL 或其他较大改造。

## 5. 性能测量与验收

### 测量方式

在实际 Windows 桌面应用中，连续按住鼠标扩张、收缩选区，包含反向拖动和跨屏，每组至少 10 秒、重复三次。记录应用构建类型、屏幕布局、刷新率、Windows 缩放、应用倍率、显卡和放大镜状态；优化前后使用同一环境与操作方式。

测量应包括：

- 实际可见 WebView 的空闲 `requestAnimationFrame` 间隔中位数 `T`，作为当前运行环境的帧预算参考。
- 拖动时的帧间隔分布、超过 `1.5T` 的比例、超过 `2T` 的长间隔数量。
- 输入状态处理、选区更新、放大镜采样/绘制、浮层布局等 JS 阶段的 p50、p95 和 p99 耗时。
- 每次拖动的首帧等待与稳定拖动阶段分别记录，保留首次捕获和窗口复用两种情况。
- 浏览器 Performance 跟踪中的绘制、合成和长任务。Canvas 方法返回耗时只代表部分提交成本，不能单独作为 GPU 耗时或实际 FPS 的证明。
- 重复捕获后的画布、采样缓存数量与内存趋势，检查关闭时是否释放。

采样写入有限容量缓冲，测试结束后一次输出，避免逐帧日志干扰测量。无界面浏览器可以验证状态、绘制调用和像素，但最终流畅度结论来自真实 WebView2 和用户体验。

### 验收目标

以下是目标，尚非已取得结果：

| 指标 | 目标 |
| --- | --- |
| 拖动观感 | 在用户原来感觉不丝滑的双屏环境中，选框连续跟随明显改善；放大镜开启也可用 |
| 拖动帧间隔 | 稳定阶段 p95 ≤ `1.25T`，超过 `1.5T` 的比例 < 5%；若设备空闲时已不稳定，单独报告环境基线 |
| JS 工作预算 | 拖动更新 p95 争取 ≤ `0.4T`，为绘制与合成留出余量；60 Hz 约为 6.7 ms，120 Hz 约为 3.3 ms |
| 绘制路径 | 源数据及布局不变时，纯框选和放大镜移动不执行整幅底图清空或复制 |
| 最终落点 | 抬起鼠标时的最终选区与事件坐标一致，待处理帧不能覆盖最终状态 |
| 图像结果 | 原始分辨率和导出像素保持正确，辅助显示层不进入输出 |
| 生命周期 | 连续开关截图 20 次，各层不累计，旧捕获的像素和待处理输入按会话释放 |

如果仍达不到流畅度目标，应附上性能跟踪和未达标原因，继续针对剩余瓶颈优化；不以单次平均 FPS 或无界面测试结果宣告验收。

## 6. 回归清单与风险处理

功能回归至少覆盖：

- 单屏 1080p、双屏 1080p、单屏 4K；有相应设备时补充双 4K、高刷新率和混合刷新率。
- 负坐标副屏、纵向错位、混合 DPI；应用倍率 100%、125%、150%。
- 普通截图的初次框选、反向框选、跨屏框选、窗口自动框选、重新框选及已选区域移动。
- 松开前仍有待处理帧、没有最后一次鼠标移动事件、关闭或刷新发生在拖动期间。
- 放大镜开关、屏幕边缘避让、跨屏取色、复制颜色反馈。
- 标注、马赛克、文字、撤销和重做；复制、保存、OCR 及分享输出。
- 进入/退出滚动截图，确认捕获区为真实透明区域，新增底图没有覆盖它。
- 前一轮双屏尺寸同步修复，保持显示前就绪校验有效。

主要风险是新增层的显隐与坐标不一致、合成层增加内存，以及透明滚动捕获区被底图遮住。用同一套显示模式管理各层，避免源画布重复分配，并以跨屏像素和透明区域检查覆盖这些边界。

实施完成后运行 `npm run check`；只有涉及 Rust 的修改才追加对应 Rust 检查。记录实际桌面性能结果，并更新 `docs/architecture.md` 中的当前渲染说明。本提案保留日期和实施状态，未发布改动不写入 `CHANGELOG.md`。
