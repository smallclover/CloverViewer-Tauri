## 应优先修复的问题

### 1. [P1] 长截图导出提前消耗唯一结果，复制后不能再保存，失败后也无法重试

位置：[结果取出](../src-tauri/src/scroll_capture/tauri.rs#L107)、[导出入口](../src-tauri/src/scroll_capture/tauri.rs#L542)、[前端复制后保留面板](../src/screenshot/scroll-capture-controller.ts#L298)。

`finish_scroll_capture` 在检查动作、写磁盘或写剪贴板之前调用 `take_result()`，直接把后端结果置空。前端复制成功后继续保留结果面板，下一次点击保存或复制却会报“没有可保存的滚动截图结果”；首次导出失败也会丢掉重试所需结果。

建议：会话用 `Arc` 持有不可变结果；导出只借用/克隆引用。明确取消、开始新截图或确认离开时再清除结果，前端导出期间禁止重复提交。

验收：完成长截图后复制两次再保存；模拟首次剪贴板失败后重试；结果一直保留到明确结束会话。

### 2. [P1] 编辑保存完成时无条件清除 dirty，会漏掉保存期间新增的修改

位置：[saveTo](../src/viewer/image-editor-controller.ts#L481)。

保存 PNG 和后端落盘都需要异步等待，期间画布仍接受输入；成功返回后直接执行 `dirty = false`。如果用户在等待期间加了新标注，这些内容不在刚保存的快照里，却也被认定为已经保存，随后退出不会询问。

隔离复现：启动覆盖保存 → 后端保存暂挂 → 再画一个矩形 → 保存返回 → Esc。结果为 `closedWithoutDiscardPrompt: true`，仅出现之前的覆盖确认。

建议：用编辑修订号记录保存快照，只有当前修订等于保存修订时才清除未保存状态；同时设保存忙碌状态，防止并行覆盖、退出和上一会话的回调更新新会话。保存对话框返回后也需核对会话和所选格式。

### 3. [P1] 打开其他内容的入口没有统一经过未保存修改确认

位置：[目录打开](../src/main.ts#L212)、[文件拖入](../src/main.ts#L686)、[截图打开桥接](../src/main.ts#L836)、[历史导航按钮](../src/ui/page-navigation-controller.ts#L60)。

编辑器自己的 Esc/退出按钮有确认框，但拖入另一个文件、截图/OCR 的“在查看器打开”事件，以及仍可点击的历史导航按钮，直接切换视图或目录。再次进入编辑会清空 `shapes` 和历史，已有修改无法恢复。

建议：所有离开编辑会话的入口共用一个异步导航守卫。确认继续编辑时保持原会话；截图结果可以先暂存待打开请求，避免外部事件强制替换正在编辑的内容。真正关闭应用且不隐藏到托盘的路径也应纳入守卫。

验收：带未保存标注时分别拖图、点击历史后退、打开新截图、关闭应用，均可选择保留当前编辑。

### 4. [P1] 更换热键先注销旧键，新键注册失败后没有恢复

位置：[普通截图热键](../src-tauri/src/commands.rs#L182)、[长截图热键](../src-tauri/src/commands.rs#L217)。

新组合被其他应用占用时，注册返回错误，但原组合已注销；配置仍显示旧组合。再次填写旧值会因 `old == hotkey` 提前成功返回，实际仍未注册。滚动截图启动时的备用热键又只保存在局部变量中，后续设置可能无法注销实际生效的备用键。

建议：维护“用户偏好”和“实际注册键”，按解析后的 Shortcut 比较冲突。优先注册新键，成功后注销旧键；必须先注销时，需要明确回滚。设置与快捷键说明应能反映实际生效的组合。

## 其他明确问题

### 5. [P2] 覆盖图片后，后端缩略图内存缓存仍返回旧内容

位置：[内存 key](../src-tauri/src/thumbnails.rs#L94)、[保存后的刷新](../src/main.ts#L165)。

前端清了缩略图缓存，但 Rust 内存 key 只有 `path#size`，会在检查带修改时间的磁盘缓存之前命中旧图。同一应用进程中覆盖原图、重新进入网格或预览条，仍可能展示旧内容。

建议：统一用路径、文件大小和高精度修改时间构成缓存版本，或者覆盖成功后精确失效所有层的该路径缓存。前端 `clear()` 还应使旧的在途任务失效，防止清空后又被旧结果填回。

### 6. [P2] 取消截图后，尚未完成的分享请求仍能创建链接和更新面板

位置：[shareImage](../src/screenshot/screenshot-action-controller.ts#L121)。

导出和 OCR 都有 `busy/generation` 保护，分享流程却未使用它们。取消、清空或开始下一会话时，旧的 PNG 编码和创建分享仍会继续。

隔离复现：`shareImage()` → `reset()` → PNG 编码完成。后端创建分享次数为 1，旧面板展示次数也为 1。

建议：分享纳入同一忙碌状态和会话编号；编码后、后端返回后都校验。后端分享需具备可按请求撤销的 ID，避免旧请求完成时停掉或替换新分享。

### 7. [P2] 编辑器矩形、椭圆、箭头没有提交 pointerup 的最终位置

位置：[pointerup](../src/viewer/image-editor-controller.ts#L607)。

仅当 `current.points` 存在时才读取抬起坐标，其他工具沿用最后一次 pointermove 的位置。快速拖动、输入合并时，最终标注会比鼠标实际松开的位置短一截。编辑器绘图也缺少 `pointercancel/lostpointercapture` 的状态收尾。

隔离复现：预览比例 0.2，下移到 `(300,200)` 后在 `(400,250)` 松开，实际结束源坐标 `(900,600)`，应为 `(1400,850)`。

建议：所有绘图工具先同步最终坐标再提交；取消捕获时丢弃当前笔画、清理拖动状态和待绘制帧。

### 8. [P2] 同一次 Esc 会触发两份查看器后退处理

位置：[第一处](../src/main.ts#L539)、[第二处](../src/main.ts#L751)。

两个 window keydown 监听都会调用 `pageNavigation.back()`，前者没有标记事件已处理，后者也没有检查 `defaultPrevented`。当图片导航历史超过一层时，一次 Esc 连退两步。

使用实际两份处理器复现：历史索引从 2 一次变为 0，`backCallsForOnePress = 2`。

建议：统一 Esc 的处理顺序，并确保一次按键只由一个层级消费；覆盖弹窗、设置、编辑器、单图和网格的测试。

### 9. [P2] 目录加载缺少序号，较早的慢请求会覆盖较新的选择

位置：[openDirectory](../src/main.ts#L212)。

单图加载和编辑源加载都有过期结果保护，目录加载没有。先请求 A 再请求 B，若 B 先完成、A 后完成，最终会回到 A。外部事件和拖入文件都能触发这条路径。

使用实际函数和受控 Promise 复现，最后请求为 B，最终 `currentDir` 为 A。

建议：目录会话同样维护请求修订号，提交目录、打开指定文件、刷新保存元数据时都校验当前会话。加载失败应向调用方传播明确结果，避免打开失败后仍显示成功通知。

### 10. [P2] 配置持久化失败不会返回前端，设置仍显示“保存成功”

位置：[save_config](../src-tauri/src/config.rs#L275)、[set_config](../src-tauri/src/commands.rs#L15)、[前端乐观更新](../src/ui/settings-controller.ts#L159)。

后端保存只记录日志，命令返回 `()`；前端已经更新配置并提示成功。权限不足或磁盘不可写时，重启后设置丢失。开机自启还先保存偏好，再写注册表；写注册表失败仅反转复选框，配置没有恢复，界面和实际状态会分离。

建议：配置写入返回 `Result`，成功后提交状态；失败时回滚对应控件。跨系统副作用的设置使用专用事务路径。保存文件采用同目录临时文件与原子替换，避免截断 JSON。

### 11. [P2] 格式支持存在断层：.tif 无法选中，AVIF 浏览与原生操作能力不一致

位置：[扫描白名单](../src-tauri/src/image_scan.rs#L12)、[前端文件过滤](../src/main.ts#L587)、[复制图片](../src-tauri/src/screenshot.rs#L195)。

文件选择器接受 `.tif`，后端扫描只列出 `.tiff`，因此选中的 `.tif` 不会出现在图片列表。AVIF 可以交给 WebView 展示，但当前依赖 feature 没有 AVIF 解码所需的 `avif-native`，原生复制、分享及缩略图生成走 `image::open`，能力不一致。

建议：把可浏览、可原生解码、可编辑、可覆盖保存的能力统一定义；补齐 `.tif`。AVIF 原生操作应补适配或使用 WebView 已解码的像素，相关按钮与说明反映真实支持范围。

### 12. [P2] 图片旋转只旋转文字标注的两个坐标，文字绘制仍保持水平

位置：[transformAnnotations](../src/viewer/image-editor-controller.ts#L394)、[文字绘制](../src/image-editor/annotation-renderer.ts#L64)。

几何图形和笔画点会随旋转变化，但文字把起点、终点分别旋转后，绘制仍在新起点沿水平方向排字。90° 后的边界和文字方向不一致，靠边文字可能移到图像外，影响预览、命中与导出。

建议：给文字标注保存局部变换/角度，并让绘制、边界和命中共用变换；或在明确的旋转操作中统一转换标注图层。用靠近四边、多行文字、连续四次旋转验证。

### 13. [P2] 覆盖原图仍直接截断目标文件，写入失败时可能损坏原图

位置：[save_edited_image](../src-tauri/src/commands.rs#L436)。

编码已先在内存完成，能够保护编码失败的情况；最终 `fs::write` 仍会先截断原文件。磁盘写满、存储设备断开或中途写入失败时，用户唯一的原图可能只剩部分数据。

建议：先在目标同目录创建唯一临时文件，完整写入并同步，再用适合 Windows 的原子替换操作提交；失败保留原文件，清理临时产物。需要写失败/替换失败的集成测试。

### 14. [P2] 超长笔画的边界计算会因参数展开触发 RangeError

位置：[shapeBBox](../src/image-editor/geometry.ts#L37)。

实现把全部点映射为数组，再传给 `Math.min(...xs)`/`Math.max(...xs)`。持续绘制的点数没有统一上限；传入 200,000 个点时，实际函数抛出 `RangeError: Maximum call stack size exceeded`。

建议：一次循环求边界，避免参数展开和重复数组分配；笔画历史配合内存预算，必要时对自由画笔做保真简化。截图和图片编辑共用该模块，可一起收益。

## 代码层面的优化方向

1. **耗时原生任务移出 UI 主线程。** `get_thumbnail`、`list_images`、`read_image_data`、`read_editable_image_data`、`save_edited_image`、`copy_image_file` 和长图落地目前都是同步 Tauri 命令。前端 Promise 和并发队列不会自动把这些同步函数搬到后台。已核对本地 Tauri 命令宏的同步执行路径。可参照已有 `get_image_info`/`ocr_image` 的 `async + spawn_blocking`，再限制解码并发与总像素预算。单个缩略图写入后还会扫描、读取元数据并排序整个磁盘缓存目录，应合并或节流清理。先测冷启动、大目录首屏、快速翻图、长截图复制的延迟和主线程占用，再比较修改后的结果。

2. **按字节限制所有缓存与历史。** 单图解码缓存已有 96 MB 预算，可以保留；TIFF 等 fallback data URL 缓存按 20 张计数，Rust 缩略图按 512 条计数，没有实际字节预算。大图的 Canvas、原图、标注层和 PNG/Base64 还会同时存在。撤销历史每步深拷贝全部笔画，50 步上限不能代表固定内存。建议统一记录内存成本，历史使用不可变对象共享或操作记录；关闭编辑器时释放大画布，重新进入再初始化。MCP 返回图片的重新解码/编码目前也仍在异步处理器中同步运行，应连同文件维护放入受控后台任务。

3. **收紧实际启用的依赖 feature。** `cargo tree -e features -i image` 显示，虽然直接依赖 `image` 关闭了默认 feature，`imageproc` 默认配置又启用了 `image/default`、`text`、`fft`，把 AVIF 编码、EXR 等编解码链重新带入。业务只在 OCR 中调用 `gaussian_blur_f32`。可以从 `imageproc` 的最小 feature 组合验证构建和 OCR 行为，再比较编译耗时、产物大小与性能，不能只看直接依赖的配置就判断裁剪成功。

4. **围绕职责逐步提取模块。** `image-editor-controller.ts` 适合提取保存事务、标注输入和文本布局；`main.ts` 适合提取目录会话及导航守卫；`commands.rs` 适合拆分配置、热键、图像 IO、缓存维护。当前已有共享几何、标注图层、加载器和截图状态模块，边界总体合理，没必要仅为行数做大规模改写。

5. **统一开发与 CI 的运行时。** README 要求 Node 24，quality/release workflow 仍配置 Node 20；安装的 Vitest 5.0.2 声明 Node `^22.12.0 || ^24.0.0 || >=26.0.0`。当前测试实际使用 `node:test`，没有调用 Vitest。应选择一致的工具链并移除未使用依赖，减少引擎警告与维护面。发布工作流应把质量门禁和生产构建纳入发布前验证。

## 功能层面的后续改善

这些是功能建议，不计入上面的确定缺陷：

- **编辑器增加显式缩放。** 当前可自动适配和放大小图，但没有编辑中的滚轮缩放、缩放百分比、适应窗口/100% 和平移入口。精细裁剪或修图时，用户仍受自动适配比例限制。应保留拖动时变换稳定和固定屏幕尺寸手柄的现有设计。
- **外部文件变化可刷新。** 现在浏览列表主要在打开目录和覆盖当前图片后更新。可先提供 F5/刷新按钮，再决定是否加入文件监听；增删或修改后保持当前路径、排序和滚动位置，另存副本后也应能在当前目录出现。
- **主题跟随系统实时变化。** 主界面和截图只在应用配置/刷新时读取 `prefers-color-scheme`；主窗口长时间打开时，没有监听系统主题变化。提取共享主题控制器，处理 media query 的 change 事件。
- **导出预期更明确。** JPEG 质量、透明区域背景色、EXIF/ICC 保留策略，以及 GIF/WebP 动画编辑后成为静态图的行为，应有一致且可理解的说明；调整文字时同步中英日三语。
- **分享面板反映真实状态。** 下载一次后后端已停止，面板仍按剩余时间倒计时；建议提供已失效状态。选择网卡和分享图片方向也应实测，原生复制/分享目前没有复用缩略图的 EXIF 方向校正。
- **资源上限提前执行。** 手动长截图已有按宽度计算安全高度，自动模式则主要在完成时检查字节数。可以统一预算，在追加前限制，达到上限时保留已有结果，减少超宽区域到最后才失败的情况。

## 建议实施顺序

1. 先处理 1–4：保留长截图结果、保存修订号、统一编辑离开守卫、热键事务；给故障和取消路径补回归测试。
2. 再处理 5–14：缓存一致性、异步会话取消、输入最终提交、导航、配置、格式、文字旋转和写入完整性。
3. 然后优化主线程任务、缓存预算、依赖 feature 和 CI 工具链；基于同一组图片目录与截图记录前后指标。
4. 最后补编辑缩放、刷新、主题与导出体验；做 Windows 真机、多屏与 DPI 回归。

已有的虚拟网格、当前图片优先加载、OCR 后台线程、标注图层缓存、裁剪逐帧合并输入、更新下载重试与签名校验可以继续沿用。当前最有价值的投入集中在异步事务、会话生命周期和数据保存完整性。
