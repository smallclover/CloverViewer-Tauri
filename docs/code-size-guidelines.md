# 项目开发规范：业务源码文件行数

## 目的

控制单个业务源码文件的规模，使职责边界清晰、代码评审可读、测试定位直接，并降低修改同一文件时的冲突概率。
行数不是质量的唯一指标：内聚性、复杂度、依赖方向和可测试性优先于机械拆分。本规范将行数作为需要进一步检查的预警信号。**不要只为满足行数而拆分**：职责单一、结构和注释清楚、依赖合理的文件，即使略高于目标也可以保留。

## 适用范围与统计口径

本规范适用于产品运行时的业务源码：`src/**`、`src-tauri/src/**`，以及后续新增的同类目录。

- 以**有效代码行**为准：不计空行和仅包含注释的行；包含可执行语句、声明、标记和带行内注释的代码行。
- 不适用于自动生成代码、锁文件、配置文件、文档、图标和图片资源。
- 单元/集成测试、一次性诊断工具、发布脚本和示例代码不受硬性限制，但仍应保持单一测试或工具目的。
- 代码规模报告可同时列出物理行数，便于快速盘点；做评审判断时应使用有效代码行。

## 目标与处理规则

| 有效代码行 | 处理方式 |
| ---: | --- |
| 不超过 500 | 业务源码的默认目标。 |
| 501–800 | 可以保留。PR 应确认文件仍只承担一个清晰职责、结构易读且测试边界明确；新增大型功能时再评估提取模块。 |
| 801–1,200 | 需要在 PR 中说明暂不拆分的原因及后续拆分点；若职责已混杂，默认在当前或紧接的迭代中拆分。 |
| 超过 1,200 | 默认应拆分；除修复缺陷或紧急发布外，不应继续向其中加入无关职责。需要维护例外说明和可执行的重构计划。 |

“超过 800 行需说明、超过 1,200 行默认拆分”是软性质量门槛，不是阻塞紧急修复的流程障碍。评审者应根据变更风险决定是否允许例外。

## 允许例外

以下情况可以超过目标，但必须在文件顶部注释或 PR 描述中说明原因：

- 自动生成代码或由外部协议、SDK 直接生成的绑定代码；
- 大型静态数据表、翻译资源或兼容性映射；
- 无法安全切分且拆分会显著降低可读性的高度相关实现；
- 测试夹具、探针程序或独立维护工具。

例外不应成为继续混入新职责的理由；当文件发生较大功能修改时，仍应重新评估拆分机会。

## 推荐拆分方式

- Rust：按领域职责创建子模块，使用 `mod.rs` 或同名目录组织；将平台 API 调用、数据模型、算法和 Tauri 命令边界分开。
- TypeScript：将状态、事件处理、渲染、领域计算和 Tauri API 调用分离；一个模块只导出紧密相关的能力。
- CSS：按页面或组件分组，统一保留设计 token/全局变量，避免按单条属性机械分文件。
- 先提取低耦合、已有测试覆盖的部分；每次拆分后保持行为不变，并补充模块级测试。

## 当前基线（2026-09-22）

截图、主窗口入口与滚动截图完成职责拆分后，以下业务文件仍值得在新增功能或评审时关注：

| 文件 | 物理行 | 建议关注点 |
| --- | ---: | --- |
| `src/styles.css` | 1,312 | 按页面或组件归类，并保留独立的全局设计 token。 |
| `src/screenshot.ts` | 688 | 截图窗口的组合入口；状态、输入、绘制、工具栏、滚动截图和生命周期已位于 `src/screenshot/`。保留页面级 DOM 与跨模块编排，新增职责应优先落入相应子模块。 |
| `src/main.ts` | 440 | 主窗口组合入口；已接近 500 行的默认目标，新增逻辑优先放入 `src/viewer/` 或 `src/ui/` 的控制器。 |

滚动截图模块拆分后，`src-tauri/src/scroll_capture/` 下最大的文件是 `session_auto.rs`（348 行）、`matching.rs`（312 行）与 `session_manual.rs`（266 行），均已在默认目标内，先前的「自动会话 828 行例外」不再需要。`src/i18n.ts` 为 39 行，多语言静态数据位于 `src/locales/`。

`src/screenshot/scroll-capture-controller.ts`（310 行）与 `src/ui/settings-controller.ts`（385 行）是当前较大的前端控制器，仍低于 500 行目标；如果继续吸收新的交互状态，应优先按既有模式再提取一个模块，而不是扩大同一个控制器。

页面骨架文件（`index.html`、`screenshot.html`）不计入本规范的统计口径，但同样值得关注：`screenshot.html` 目前内联了约 950 行覆盖窗样式。后续修改覆盖窗外观时，可考虑把这段样式移到独立的 CSS 文件，与 `src/styles.css` 的分组方式保持一致。

以上文件均不要求一次性重写。优先在新增功能或修改相邻逻辑时进行小步、可验证的提取，避免高风险的大型重构。

## PR 自检清单

- 新增或明显扩大的业务文件是否仍在 500 有效代码行以内？
- 超过 800 行时，PR 是否解释了职责边界和拆分计划？
- 超过 1,200 行时，是否已拆分，或记录了明确且合理的例外？
- 提取后的模块是否拥有清晰命名、单向依赖和相应测试？
